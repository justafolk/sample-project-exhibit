# Feature test guide

Use the real Exhibit application for platform behavior and Field Store for customer application behavior. A customer fixture alone cannot validate every platform capability. The recorded results in `exhibit/VALIDATION.md` distinguish executed checks from this manual checklist.

| Exhibit capability                                      | Fixture / exercise                                                           | Expected behavior and limits                                                                                                      |
| ------------------------------------------------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Sample exploration and sign-in boundary                 | Open Exhibit and explore sample workspace                                    | Explicit sample labels; protected endpoints reject anonymous requests. Private password accounts require PostgreSQL provisioning. |
| Workspace setup                                         | Enter this repository, storefront URL, tenant and runbook in Setup           | Metadata persists within the sample session. No live GitHub installation is claimed.                                              |
| Flow authoring                                          | Create `checkout.saved-address` from `flow.yaml`, edit and delete it         | Flow metadata and actor/time history; no automatic catalog discovery.                                                             |
| Contract drafts                                         | Save complete and incomplete objects from `contracts.json`                   | Draft editing, revision and deletion; completeness does not resolve refs or grant permission.                                     |
| Preparation evaluator                                   | `npm run test:exhibit`                                                       | `ready`, `needs_info`, `not_testable`; all inputs explicitly synthetic.                                                           |
| Deterministic assertions                                | `npm test` and `npm run test:e2e`                                            | Saved address, API total, confirmation ID, rejection paths, idempotency and scoped cleanup.                                       |
| Run list, filters and URL state                         | Exhibit sample runs: filter status, search, reload; search an absent term    | Existing sample rows, preserved filters and empty states; this project cannot insert trusted runs.                                |
| Reports and provenance                                  | Open Exhibit sample report; download Markdown; inspect `/version` here       | Full SHA and gaps; unborn sample checkout reports no commit instead of inventing one.                                             |
| Local recording import                                  | Import a generated `test-results/**/video.webm` into Studio                  | Playback and original checksum; sample content only, no upload.                                                                   |
| Recording presentation                                  | Add chapters, change framing, edit title; export original manifest           | Metadata/presentation may change; original media bytes must retain checksum.                                                      |
| Screen capture                                          | Manually grant capture in an interactive browser                             | User gesture and capture permission required; headless tests cannot prove real desktop permission UX.                             |
| Recording metadata and activity                         | Save a manual recording and inspect recent activity                          | Origin remains manual and verification unverified; recording never changes a run verdict.                                         |
| Roles, tenant isolation, CSRF and revocation            | Exhibit auth/browser suites; provision separate private users for PostgreSQL | Demo isolation is exercised by browser tests. Durable private accounts and database boundaries need database integration tests.   |
| Artifact integrity / reports                            | After a clean commit, `npm run evidence` and `evidence_tool.py report`       | Actual local bytes and SHA checked; tamper a copied artifact to see rejection. No collector identity or redaction assurance.      |
| Health and startup                                      | `/healthz`, `/version`, Exhibit `/api/readyz`                                | Explicit readiness/provenance; no silent database fallback.                                                                       |
| Persistent storage, migrations and account provisioning | Optional Exhibit PostgreSQL workflow                                         | `make db-up`, `make migrate`, provisioning guide, `make test-integration`; never point at customer staging.                       |

## Future capabilities — not integrated

These are planned product boundaries, not tests that have passed: GitHub App installation and authenticated webhook ingress; delivery replay handling; PR `/evidence` authorization; immutable head resolution; durable scheduling, leases, timeouts, cancellation and retry attempts; disposable customer execution; scoped staging secrets; trusted artifact collection/redaction/upload/retention; verdict derivation by a trusted verifier; posting commit-bound GitHub checks or PR comments; public identity recovery and OAuth.

Field Store provides a concrete future execution target. Its reviewed-flow template, health/version endpoints, deterministic failures and cleanup let those integrations be added later without pretending they exist now. Production payments, real emails, external staging and multiple customer repositories remain outside this sample's coverage.
